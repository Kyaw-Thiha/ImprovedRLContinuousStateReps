## Per-representation analysis

### SSP (486.69)
- Search space was widened mid-run after the *original* SSP result (435.916, from an earlier/contaminated run) showed `n_rotates` pinned exactly at its old ceiling of 12 — a classic "wants more capacity" signal. `n_rotates` ceiling raised 12→20, and `n_scales` (previously hardcoded at 5, never searched) added as a real search dimension, range [3,8].
- Rerun with the widened space found 486.69, beating both the old SSP result and tile-coding.
- Winning `n_rotates=19` is one step short of the new ceiling (20) — a much weaker "widen further" signal than before (not pinned exactly at the boundary). `n_scales=5` landed at its original default, dead center of its new range — no signal there.
- **No convergence/variance data available** for this specific 486.69 result (see data-loss note).
- Cross-reference: A2C's independent search on SSP (different algorithm, same representation) found ~499.64 (near CartPole's max), with essentially zero variance (0.1% CV) and no boundary hits — suggests SSP's search space is fundamentally fine, and DQN's gap to A2C's near-perfect score is more likely an algorithmic ceiling (off-policy, bootstrapped, linear function approximation is a harder setting to converge than on-policy actor-critic) than a search-space problem.

### Tile-coding (476.398)
- Full 242-trial history intact (this run was not affected by the DB-path bug below, since it used the default sync path).
- **Convergence: strong.** Best value found at trial 114 of 242 (47% through); the remaining ~128 trials over ~7 additional hours found nothing better. Top-10 values cluster tightly (462.9–476.4).
- **Variance: low.** Reconstructed per-seed rewards for the winning config: 478.9, 483.5, 484.4, 456.1, 479.2 → std 10.4, **CV ≈ 2.2%**. Stable, not a lucky seed.
- **Boundary check:** `num_tilings=32` (max of [16,32]) and `tiles_per_dim=16` (max of [10,12,16]) both pinned at their ceilings; `iht_size=32768` sits at its *floor* (min of [32768,65536,131072]). An unusual pattern — wants finer tile resolution but *not* a bigger hash table (possibly hash collisions act as implicit regularization). A follow-up search with `num_tilings` up to 48-64 and `tiles_per_dim` up to 20-24 (keeping `iht_size` small) could plausibly improve further. Not yet attempted.
- Cross-reference: A2C's independent search on tile-coding shows the *identical* pattern — best found at trial 58/121 (48% through), then 63 more trials found nothing better, near-zero variance (0.2% CV), one boundary hit (`tiles_per_dim=16`, same as DQN). This "found early, converges hard" behavior looks like a genuine, reliable property of tile-coding on this task across both algorithms, not a fluke.

### Discrete (167.01)
- **Two independent hyperparameter searches (DQN this run, A2C previously) show the same weak-representation signature.**
- DQN search: only the single best trial's params are known (see data-loss note) — `n_bins=19` (not at the max of 23 — an interior optimum), `eps=0.052`, `lr=0.0945` (close to the old ceiling of 0.1).
- A2C's independent search (50 trials, 28 complete): best 124.59, found at trial 41/49 — **not converged**, still improving near the end. Very high variance: per-seed rewards 183.5, 62.9, 193.0, 90.5, 93.1 → **CV 42.6%**. Two boundary hits: `n_bins=23` (max) and `lr=0.939` (94% to A2C's 1.0 ceiling).
- **Root cause is architectural, not a search-space problem.** DQN here is a single linear layer (`Q=w·φ(s)`, no hidden layers). Discrete's one-hot encoding is combinatorial over all 4 CartPole dimensions (`n_bins⁴` — up to 279,841 cells for n_bins=23), so two nearly-identical states straddling a bin boundary land in completely unrelated cells with zero shared structure. The network must independently learn a value for each of tens of thousands of cells from limited training data; most are visited rarely or never. Tile-coding and SSP avoid this via overlapping, similarity-preserving features. No hyperparameter choice fixes this — it would need either a materially different discretization scheme (e.g. per-dimension one-hot instead of combinatorial) or a non-linear (deep) network capable of learning generalizing combinations from the sparse input.

## Bugs found and fixed during this run

1. **TileCoding dense-vector DQN update (fixed).** `Q=w·φ(s)` was materializing TileCoding's full `size_out`-length (up to 131,072) one-hot-ish vector every step, when only `num_tilings` (≤32) entries are ever nonzero. Switched to sparse index-based encode (`map_indices()`) + gather/scatter update in `dqnBasic.py`. Verified exact numerical match to the old dense math; 19-38x speedup depending on `iht_size`.
2. **PyTorch default CPU threading overhead (fixed).** Every DQN step does several tiny torch tensor ops; PyTorch's default multi-threaded backend was spinning up a full thread pool per call for microseconds of real work — likely worse in this container than on a typical dev machine due to a reported-vs-actual core count mismatch. Fixed via `torch.set_num_threads(1)` / `set_num_interop_threads(1)` at import time in `dqnBasic.py`. Combined with fix #1, took TileCoding from "stuck 15-30s/episode" to "4-13 episodes/sec" in production — a ~150-300x real-world improvement.
3. **OneHotRepCP (discrete) dense-vector DQN update (fixed).** Same class of bug as #1 — discrete's one-hot vector is *even* sparser (exactly 1 active entry). Same fix pattern applied (`n_active=1`, `map_indices()`). Exact numerical match (0.00e+00 diff); 1.5-14x speedup depending on `n_bins`.
4. **Optuna trial-count overshoot on pod/container restart (fixed).** RunPod pods restart their entrypoint process on any exit (success or failure) — there's no "run once and stop" primitive. `run_hparam_search_dqn.py` had no memory of prior invocations, so each restart re-ran a full `n_trials` MORE on top of whatever existed, indefinitely. Tile-coding and the original SSP run both overshot their 80-trial target by ~3x this way before being manually caught and the pods terminated. Fixed by recording an absolute `target_n_trials` once via `study.set_user_attr`, persisted in the study itself; every invocation now computes `remaining = target - current_total` and no-ops once the target is reached. Verified via simulated restarts (both the naive case and a real off-by-one from Optuna's `enqueue_trial()` creating an immediate WAITING-state row).
5. **R2 sync ignores custom `--db-path` (fixed, but too late for this run's discrete/ssp full history).** To avoid an earlier cross-study contamination bug (pods restoring from a shared legacy R2 key and picking up stray trial history from other representations), the final discrete/ssp reruns used a custom `--db-path`. `sync_to_r2.py`'s periodic and final sync calls were hardcoded to always target the default path, completely independent of `--db-path` — so the *real* trial database for these two runs was never backed up anywhere. It only existed in the pods' ephemeral filesystem and was lost the moment those pods were terminated. **Fixed**: `sync_to_r2.py trial` now accepts `--db-path`, and `run_hparam_search_dqn.py` passes its actual active `DB_PATH` through on every sync call (periodic and final). Not yet re-validated with a live rerun.
6. **Local best-params files clobbered production R2 results (fixed, self-inflicted, caught immediately).** While investigating bug #5, discovered that an earlier local test run (fake-objective test, done to verify the trial-count-overshoot fix) had left stale/garbage values in `outputs/hparam_search/best/dqn_discrete_none.yaml` and `dqn_ssp_none.yaml` on the local machine. Running `sync_to_r2.py phase stage0_cartpole` as a "final sync" after the real reruns completed blindly uploaded this stale local directory, overwriting the correct 167.01/486.69 results in R2 with test garbage. Caught by directly verifying R2 server-side content; corrected by re-uploading the true values (recovered from container log output captured during monitoring). No permanent data loss for the best-value results, but a reminder that local dev/test runs share output paths with "production" sync targets — no isolation exists between them.

**Net effect on data completeness:** best-value results are correct and trustworthy for all three representations. Full trial-by-trial history (needed for convergence/variance/boundary analysis) is only available for tile-coding; discrete and SSP's final winning-configuration runs have no recoverable trial history and would need a rerun (with fix #5 now in place) to regenerate it.

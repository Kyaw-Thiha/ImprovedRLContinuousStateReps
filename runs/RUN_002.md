# RUN_002 — DQN v4 Hyperparameter Search (CartPole-v1)

**Scope:** 18-cell grid — 3 representations (discrete, SSP, tile_coding) × 3 centering
modes (none, simple, value) × 2 architectures (linear, deep). Each cell: independent
500-trial Optuna search (`TPESampler`+`MedianPruner`, single seed per trial), followed
by a post-hoc re-evaluation of the top candidates across 10 fresh seeds to filter
lucky-seed search winners. Methodology follows Raffin's two-part Optuna guide
(`docs/06-related-work.md`). Full design docs in `docs/`; original session handoff in
`docs/HANDOFF_dqn_v4_search_2026-09-29.md`.

**SUPERSEDED by `runs/RUN_003.md` (2026-10-06): the greedy re-filter and 20-seed final eval of all 18 cells are recorded there.**

~02:30 UTC. The remaining 9 cells (listed below) will be rerun together in a future
session — this file should be updated as that data comes in.

## Bugs found and fixed during this run

1. **Tie-break bug (fixed).** CartPole-v1's 500-step reward cap means many trials
   saturate the search-phase score exactly. When more than `top_k` (10) trials tied at
   the max, the old `sorted(...)[:top_k]` degenerated into "whichever 10 trials have
   the lowest trial number" — arbitrary. Fixed: `_select_reeval_candidates()` now
   expands to a pool of up to `TIE_EXPANDED_POOL_SIZE=20` when ties exceed `top_k`,
   ranked by `episodes_to_learn` where recoverable, random-filled otherwise.
2. **Reeval-stats persistence gap (fixed).** `reevaluate_top_trials()` computed
   mean/std for every candidate but only ever printed non-winners to stdout —
   permanently lost once a pod terminated. Fixed: now writes `reeval_results.json`
   (full rank/trial/mean/std/params table) into the reeval data dir, riding along on
   the existing R2 sync.
3. **Bug #2 — mid-reeval hang (still unconfirmed root cause).** Recurred again this
   session (`tilecoding/value/linear`), same signature as before: cpu≈0, no new log
   output, no sync message, happens after the tie-expansion print but before the first
   reeval candidate's 10-seed loop completes. This occurrence caused the one real data
   loss of this run (see table above). Nobody has done a `py-spy` capture on an
   SSH-enabled pod yet — moot now since it turns out **no pod in this run ever had
   sshd running** (no `startSsh` was set on any `create-pod` call, and the image's
   entrypoint execs Python directly as PID 1 with no supervisor) — so live debugging
   this bug will need a pod explicitly launched with SSH enabled next time.
4. **R2 periodic-sync staleness during active search (newly observed, root cause not
   diagnosed).** `tilecoding/value/linear`'s R2-synced trial count was seen to
   regress (463 → 303) and then stay frozen at exactly 303 across several repeated
   checks over ~30 minutes, even while its own `LastModified` timestamp on R2 kept
   advancing (i.e., something was re-uploading the *same* stale content repeatedly,
   not failing to sync outright). Distinct from the well-understood "reeval doesn't
   sync until the end" behavior — this one happened during search itself, when
   periodic sync should have been current. Not root-caused this session.

## Open methodology issue: RESOLVED (2026-10-04/05)

The winner's-curse diagnosis that used to be here (reeval pool drawn only from trials tied at the exact
max score) was incomplete: the old filter also scored a different, noisier metric (epsilon-greedy online
return) than the search selected on. Both are fixed — candidates are now ranked by the last 5 GREEDY
checkpoints from the Optuna DB, the filter and final eval are greedy, and the filter is flat top-20 x 10
fresh seeds, followed by a 20-seed final eval. See `docs/handoffs/02-dqn-v4-greedy-refilter-plan.md`
and decision log entries 14-18. Results from this run's original reeval (the table above) are
online-metric numbers and are superseded by the `_v2` outputs on R2 under
`stage0_cartpole/refilter_v2/` and `stage0_cartpole/best_params/*_v2.yaml`.
